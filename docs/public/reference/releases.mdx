Slopsentral uses one product version for authored plugins, checkout tooling, and provider archives.
`package.json` owns that version.
Release Please proposes one patch increment for the root component.
Dependency pins and schema revisions keep separate versions.

A release promotes tested retained bytes.
Publication never rebuilds the candidates or replaces conflicting existing assets.
The [release concept](/knowledge/operations/releases) explains the source-to-artifact relationship.

## Version PRs and publication

1. A main push starts `Validate Source` for its exact source revision.
2. Successful qualification keeps provider archives, the Pi package, installer assets, and source-bound receipts.
3. `Release Slopsentral` admits an unpublished shared version from a successful main run.
4. The publisher admits the original producer and every candidate digest.
5. It publishes those bytes under `slopsentral-vX.Y.Z`.
6. It examines actual downloads before the release becomes current.
7. It completes the matching merged version PR's labels.
8. `Release Please` proposes the next version after a successful release workflow.

A successful release workflow can report that no new release is needed.
Ordinary commits cannot republish an existing version.
A failed main run keeps an unpublished increment pending for repair.

Release Please version PRs have a separate admission rule.
The PR must come from the configured App and advance one patch.
Its exact head must pass both validation jobs.
It can change only declared version files and `CHANGELOG.md`.
Forks, drafts, stale heads, and mixed source changes fail admission.
Ordinary code PRs keep their normal merge process.

The App token makes a merged version PR trigger normal main validation.
The publisher then uses the candidates from that source run.
`autorelease: pending` remains until publication succeeds.
Completion adds `autorelease: tagged` and removes the pending label.
The matching PR must belong to the released source history.

[Release configuration](https://github.com/amichne/slopsentral/blob/main/release-please-config.json) owns the complete version-target set.
It includes root npm and Python metadata, both lockfiles, canonical plugins, and marketplace plugin references.
Generated provider trees are not version-update targets.
A new plugin needs a declared version target.

[Publish Harnesses](https://github.com/amichne/slopsentral/blob/main/.github/workflows/publish-harnesses.yml) separately maintains provider branches and the Codex/Copilot trees on main.
Those branches advance. A stable release archive remains immutable.
Historical Pi `0.1.N` releases also remain immutable.
The unified version line starts at `4.0.1`.

## Required GitHub App setup

Release PR creation needs a repository-scoped GitHub App installed on `amichne/slopsentral`.
Grant Contents, Pull requests, and Issues read/write access.
The workflow needs no webhook, administration permission, or Actions-write permission.

Store these values through GitHub's private secret interface:

| Secret | Content |
| --- | --- |
| `RELEASE_PLEASE_APP_ID` | Numeric App ID |
| `RELEASE_PLEASE_APP_PRIVATE_KEY` | Complete PEM private key |

The job creates a repository-scoped token and revokes it afterward.
It does not reuse that token for release publication.
The workflow has no fallback to `GITHUB_TOKEN` for version PR creation.
Never put credentials in source, issues, or session text.
A local workflow result cannot establish remote secret configuration.

For an authorized retry on main, use:

```sh
gh workflow run release-please.yml --repo amichne/slopsentral --ref main
```

## Verification and recovery

For a release-policy change, run:

```sh
npm run check:release
node --test tools/tests/release-please.test.mjs
uv run --locked pytest tools/python_checks/test_release_version.py tools/python_checks/test_release_assets.py tools/python_checks/test_pi_release_workflows.py
```

The updater test uses the action's exact Release Please library version.
It changes a disposable checkout and makes sure that uv accepts the resulting lock unchanged.
Keep the dependency pin, action pin, and updater assertions aligned.

A failed qualification run supplies no publication authority.
If a version PR merges before failure, repair the cause through a normal PR.
The next successful main run can publish that still-unpublished version.
The publisher completes the original version PR even when the released source includes that repair.

Interrupted publication can leave a tag or draft.
Inspect that state before retry and preserve conflicting existing bytes.
If publication succeeds but labels fail, examine downloads before the idempotent label-finalization operation.
Do not remove a pending label to imply publication success.

[Version selection](https://github.com/amichne/slopsentral/blob/main/tools/release_version.py) owns version and PR admission.
[Provider candidates](https://github.com/amichne/slopsentral/blob/main/tools/release_assets.py), [Pi candidates](https://github.com/amichne/slopsentral/blob/main/tools/pi_candidate.py), and
[setup packaging](https://github.com/amichne/slopsentral/blob/main/tools/setup_assets.py) own their receipts.
The [publisher workflow](https://github.com/amichne/slopsentral/blob/main/.github/workflows/release-pi.yml) composes those owners.
Setup receipts accept historical two-file and current five-file inventories, with complete inventory and duplicate-name rejection.
Receipt schema 2 binds the version to `package.json` at the admitted source commit.
Run identity and producer attempts remain separate facts.

Use the [Pi recovery guide](/guides/pi#scope-updates-and-recovery) for consumer rollback.
Local tests establish policy and candidate behavior. An actual hosted run and download establish publication.
