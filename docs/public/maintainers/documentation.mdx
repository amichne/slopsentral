`docs/public` contains the Mintlify site.
`docs/public/docs.json` owns navigation, colors, and assets.
Plugin contracts remain under `source/`.
`docs/pi-harness.md` owns the generated public Pi guide.
After a Pi guide change, run `npm run docs:sync`.
Do not edit `docs/public/guides/pi.mdx` directly.

## Prepare and preview

Use Node.js 24.21.0 for the pinned Mintlify CLI.
From the repository root, install the locked dependencies:

```bash
npm ci
```

Start the local site:

```bash
npm run docs:dev
```

Open the URL that the command reports.
Examine the Guide, Reference, and Maintainers tabs.
Use each changed page's links and controls.

## Examine a change

From the repository root, run:

```bash
npm run docs:check
```

The command rejects stale Pi output, then runs Mintlify build assessment and internal-link assessment with anchors and redirects.
The `Validate Documentation` workflow runs the same command for documentation changes.
A passing result does not prove source accuracy or reader comprehension.

Assess changed prose with the [writing procedure](/guides/controlled-writing).
Keep the report and input hashes outside the public site.
Examine domain terms against their source separately.

## Examine the browser result

Open the URL printed by `npm run docs:dev` in your browser.
Use a separate tab for the preview so you can compare it with the public site.

Use the page controls to reach the changed guide.
Examine the rendered heading and command text after navigation settles.
Use a narrow viewport to examine mobile navigation and horizontal overflow.

Keep browser evidence separate from Mintlify build results.
A local preview does not prove that the public deployment serves the same source.

## Deployment source

The public site is [slopsentral.michne.com](https://slopsentral.michne.com).
Use `amichne/slopsentral`, branch `main`, directory `docs/public` for the production deployment.
Connect that source after the documentation change merges.
Keep the content directory as `docs/public`.
The Mintlify GitHub app must include `amichne/slopsentral` in its selected repositories.

Mintlify refuses workflow access on the current plan because it lacks the WORKFLOWS entitlement.
That refusal prevents automatic Mintlify drafts.
The `Draft Documentation Updates` workflow supplies a separate path for the Pi guide.
A push to `main` that changes its canonical guide or generator starts the workflow.
It regenerates the public page and creates or refreshes one draft on `automation/pi-docs`.
The draft contains only `docs/public/guides/pi.mdx`.
Other pages still need source review and authored changes.

The workflow explicitly starts `Validate Documentation` for a changed bot branch.
GitHub suppresses ordinary workflow triggers from PRs that use `GITHUB_TOKEN`.
The explicit dispatch avoids a draft without documentation evidence.
The workflow never merges the draft or changes deployment settings.

GitHub Actions must have permission to create pull requests in the repository settings.
The repository enables bot-created PRs and keeps the default token permissions at read-only.
The job needs content, pull request, and action write permissions for its draft and assessment dispatch.
The normal documentation job uses read-only permissions.
