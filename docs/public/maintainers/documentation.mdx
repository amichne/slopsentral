Slopsentral treats documentation as part of software design and maintenance.
A change connects its consumer, invariant, implementation, executable evidence, and explanation.
Use that connection to understand the system before a change and examine its effects afterward.

## Choose the owner

[OpenWiki](/knowledge/quickstart) owns the repository's OKF explanations.
Its native lifecycle owns page assignments, Claims, source versions, indexes, and finalization.
The guides in `docs/` own operational commands and recovery procedures.
The [glossary](/reference/glossary) supplies provisional definitions from `glossary.json`.
Generated provider trees and installed caches consume these authored sources.
The [Mintlify site](/maintainers/site) also consumes the canonical guides and OKF pages through a checked projection.

[OKF](https://github.com/GoogleCloudPlatform/knowledge-catalog/blob/main/okf/SPEC.md) represents concepts as Markdown with YAML frontmatter.
The bundled validator implements its established minimal format contract.
OpenWiki 0.6.1 owns this repository's producer fields and versioned Claims.
This workflow does not claim complete support for every optional field in the evolving upstream specification.

Use the existing store in another repository.
Create a new store only for an authorized documentation task with no existing owner.
An ordinary code task needs focused retrieval and impact review, without an automatic full rewrite.

## Use the distributed practice

Code Knowledge Base ships the runtime, dependency lock, configuration schema, adoption procedure, and complete example project.
The [portable procedure](/maintainers/portable-documentation) supports a different project layout and a standalone OKF store.
It needs no Slopsentral checkout or OpenWiki state for that backend.
An OpenWiki project keeps its native lifecycle.

Slopsentral uses that same authored runtime through `bin/slopsentral-docs`.
Project policy lives in [coverage.json](https://github.com/amichne/slopsentral/blob/main/docs/coverage.json), without a checkout-only implementation.
The [package tests](https://github.com/amichne/slopsentral/blob/main/tools/tests/documentation-portability.test.mjs) exercise the shipped runtime in independent projects through all four provider projections.
They prove byte identity and portable command behavior, without host registration or model calls.

## Connect a change to its explanation

1. Read the owning code, public contract, callers, and focused tests.
2. Read the smallest existing explanation that describes the changed mechanism.
3. Name the consumer, invariant, accepted behavior, rejection case, and evidence limit.
4. Trace one real path across the affected owners.
5. Change the implementation and its faithful executable evidence within the authorized scope.
6. Refresh affected explanations, operational steps, and conceptual links.
7. Complete the native page queue when the affected explanation belongs to OpenWiki.
8. Examine documentation structure, links, freshness, terminology, and prose.
9. Record reviewed inputs after the source review and native finalization.

A useful explanation describes the mechanism and its reason.
It connects entry points, state transitions, failures, recovery, and neighboring concepts where those details matter.
A directory inventory cannot establish that coverage.
Keep current behavior, accepted decisions, examples, historical results, and unknowns distinct.

## Maintain the coverage map

[coverage.json](https://github.com/amichne/slopsentral/blob/main/docs/coverage.json) maps each maintained area to source selections and documents.
Schema version 2 also declares the knowledge backend, source roots, document roots, entrypoints, auxiliary pages, and fingerprint exceptions.
The bundled [schema](https://github.com/amichne/slopsentral/blob/main/source/skills/code-knowledge-base/references/documentation.schema.json) describes the external shape.
The runtime also rejects invalid path relationships and missing inputs.
A selection names one exact file or a directory prefix with a final slash.
Each area needs nonempty sources and at least one OKF explanation.
Each authored guide needs an area or an explicit historical classification.
Source files under `source/`, `tools/`, and `.github/workflows/` need an area.

The map establishes declared coverage.
It does not establish that the prose explains every branch or caller.
Add conceptual links that support the reader's next decision.
Keep local Markdown links and heading anchors valid after a rename.

Historical audits remain under their existing paths.
Their dates, model identities, results, and limits describe those historical runs.
They do not establish current measurements or current host behavior.
The [documentation index](/guides/overview) separates those records from current guides.

## Examine freshness

The [documentation command](https://github.com/amichne/slopsentral/blob/main/source/skills/code-knowledge-base/scripts/documentation.py) supplements native Claims with a repository-wide review record.
It reads Git's tracked and unignored file inventory, including local new files.
It compares reviewed source and document fingerprints with `knowledge.lock.json`.
New, changed, renamed, and deleted selected inputs invalidate that record.

```sh
mise exec -- slopsentral-docs check
```

`CURRENT` means that the selected fingerprints match the record.
`STALE` names affected areas and paths.
`REJECTED` reports invalid configuration, absent inputs, missing coverage, broken links, invalid OKF, or incomplete native state.
An active `.run.json` or a checkpoint without `status: complete` rejects admission.
Every wiki concept needs a nonempty native Claim set.

The command reads native sidecars without changing Claim identities or evidence versions.
It does not replace OpenWiki's source resolver or semantic review.
Its local link procedure examines Markdown links, reference links, images, and heading anchors.
External URLs and embedded HTML links need separate examination.
Historical audit links remain historical and receive no live-link guarantee.

This project explicitly excludes product-version fields in canonical plugin manifests and marketplace references through `fingerprintIgnores`.
The portable runtime has no implicit Slopsentral paths or version exceptions.
Every other field still affects the fingerprint.
This exception permits Release Please's existing version-only updates.
Version admission and synchronization remain with the [release owner](/reference/releases).

After source review, complete OpenWiki's native lifecycle and examine the source diff.
Then record the reviewed inputs:

```sh
mise exec -- slopsentral-docs record
mise exec -- slopsentral-docs check
```

`record` refuses broken structure and unfinished native state.
It also rejects every prepared input as a lock target and preserves foreign existing targets.
Owned receipts carry the `KNOWLEDGE_REVIEW` kind and a valid digest map.
It records a review assertion, without proof that a reviewer understood every statement.
Never use it only to silence a stale result.
Review the resulting lock diff alongside the affected pages.
Record a no-change reason in the PR description or an existing task review receipt.

## Complete an OpenWiki rewrite

Use the external `openwiki` integration from the exact Git root.
Start or resume the durable run, submit the page plan, and consume assigned pages sequentially.
Each material Claim cites current repository evidence.
Keep unchanged Claim identities.
Recheck stale Claims before confirmation, revision, or retraction.
Finish only after every page job succeeds.

OpenWiki owns its generated indexes, sidecars, provenance, and checkpoint files.
The standalone OKF utilities support other bundles.
They cannot substitute for native OpenWiki submission and finalization.
See [the native procedure](/knowledge/workflows/documentation) and [backend handoff](https://github.com/amichne/slopsentral/blob/main/source/skills/code-knowledge-base/references/knowledge-backend-handoff.md).

## Examine prose and report evidence

```sh
mise exec -- slopsentral-prose changed
uv run --locked --script source/skills/controlled-technical-writing/scripts/check_glossary.py docs/glossary.json --check-render docs/GLOSSARY.md
npm run check:docs
```

The prose command uses the pinned Vale 3.24.0 procedure and repository glossary.
Keep its JSON report and review findings at their reported locations.
`ASSESSED` describes a completed assessment, without a promise of clean prose.
A readability score cannot establish comprehension.

The [focused tests](https://github.com/amichne/slopsentral/blob/main/tools/python_checks/test_documentation.py) exercise real temporary repositories and the command interface.
They cover accepted input, source drift, page drift, broken links, missing coverage, invalid OKF, and unfinished native state.
CI and `npm run verify` run the same documentation gate.
A generated documentation PR still needs source review and an updated review record before admission.
No documentation command installs a plugin, publishes a release, or changes a deployed site.
The separate [site procedure](/maintainers/site) examines deployable input and current live content before a website publication claim.
